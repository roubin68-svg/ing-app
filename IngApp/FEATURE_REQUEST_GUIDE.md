# 📝 راهنمای درخواست قابلیت جدید (Feature Request Guide)

این راهنما به شما کمک می‌کند تا اطلاعات لازم برای توسعه یک قابلیت جدید را به صورت ساختار یافته و کامل ارائه دهید.

---

## 🎯 ساختار کلی درخواست

برای هر قابلیت جدید، اطلاعات را در **5 بخش اصلی** ارائه دهید:

1. **📋 شرح کلی و هدف**
2. **🔧 منطق کسب‌وکاری (Business Logic)**
3. **🎨 رابط کاربری (UI/UX)**
4. **🗄️ ساختار داده (Data Structure)**
5. **🔐 امنیت و دسترسی‌ها (Security & Permissions)**

---

## 1️⃣ شرح کلی و هدف

### چه اطلاعاتی باید ارائه دهید:

```
✅ نام قابلیت (مثال: "کیف پول و گردش مالی")
✅ هدف اصلی (چرا این قابلیت نیاز است؟)
✅ کاربران هدف (چه کسانی از این قابلیت استفاده می‌کنند؟)
✅ ارتباط با سایر بخش‌ها (این قابلیت با چه بخش‌هایی ارتباط دارد؟)
```

### مثال خوب:

```
قابلیت: کیف پول و گردش مالی

هدف: 
- تأمین‌کنندگان بتوانند موجودی کیف پول خود را ببینند
- بتوانند از کیف پول برای پرداخت هزینه آگهی استفاده کنند
- تاریخچه تراکنش‌ها را مشاهده کنند

کاربران هدف:
- تأمین‌کنندگان (Supplier)
- مدیر سیستم (Admin)

ارتباط با سایر بخش‌ها:
- با سیستم آگهی‌ها (هزینه انتشار آگهی)
- با سیستم کاربران (هر کاربر یک کیف پول دارد)
```

---

## 2️⃣ منطق کسب‌وکاری (Business Logic)

### چه اطلاعاتی باید ارائه دهید:

```
✅ قوانین و محدودیت‌ها
✅ فرآیندها و جریان‌های کاری
✅ محاسبات و فرمول‌ها
✅ وضعیت‌ها (Status) و تغییرات آن‌ها
✅ رویدادها و Trigger ها
```

### مثال خوب:

```
منطق کسب‌وکاری کیف پول:

1. ایجاد کیف پول:
   - هر کاربر Supplier هنگام ثبت‌نام، یک کیف پول با موجودی 0 ایجاد می‌شود
   - کیف پول به صورت خودکار ایجاد می‌شود

2. شارژ کیف پول:
   - فقط Admin می‌تواند کیف پول را شارژ کند
   - مبلغ شارژ باید مثبت باشد
   - پس از شارژ، موجودی افزایش می‌یابد و یک تراکنش "شارژ" ثبت می‌شود

3. پرداخت هزینه آگهی:
   - هنگام انتشار آگهی، اگر موجودی کافی باشد، مبلغ از کیف پول کسر می‌شود
   - اگر موجودی کافی نباشد، آگهی منتشر نمی‌شود و خطا نمایش داده می‌شود
   - هزینه آگهی: 10,000 تومان برای هر آگهی

4. تراکنش‌ها:
   - هر تغییر در موجودی باید در تاریخچه تراکنش‌ها ثبت شود
   - نوع تراکنش: شارژ، پرداخت آگهی، بازگشت وجه (در صورت لغو آگهی)
   - هر تراکنش باید شامل: نوع، مبلغ، تاریخ، توضیحات باشد

5. محدودیت‌ها:
   - موجودی نمی‌تواند منفی شود
   - فقط Admin می‌تواند شارژ کند
   - Supplier نمی‌تواند موجودی را برداشت کند
```

## 3️⃣ رابط کاربری (UI/UX)

### چه اطلاعاتی باید ارائه دهید:

```
✅ صفحات و کامپوننت‌های مورد نیاز
✅ Layout و چیدمان المان‌ها
✅ فرم‌ها و فیلدها
✅ جداول و لیست‌ها
✅ دکمه‌ها و Action ها
✅ پیام‌ها و Alert ها
✅ جریان Navigation
```

### مثال خوب:

```
رابط کاربری کیف پول:

1. صفحه "کیف پول من" (برای Supplier):
   - در منوی Supplier اضافه شود
   - نمایش موجودی فعلی (عدد بزرگ و برجسته)
   - دکمه "درخواست شارژ" (ارسال درخواست به Admin)
   - جدول تاریخچه تراکنش‌ها:
     * ستون‌ها: تاریخ، نوع تراکنش، مبلغ، توضیحات
     * فیلتر: نوع تراکنش، بازه زمانی
     * مرتب‌سازی: بر اساس تاریخ (جدیدترین اول)

2. Modal "درخواست شارژ":
   - فیلد: مبلغ درخواستی
   - فیلد: توضیحات (اختیاری)
   - دکمه "ارسال درخواست"
   - پس از ارسال، درخواست با وضعیت "در انتظار" ثبت می‌شود

3. صفحه "مدیریت کیف پول‌ها" (برای Admin):
   - لیست تمام کیف پول‌ها:
     * ستون‌ها: نام کاربر، موجودی، آخرین تراکنش
   - دکمه "شارژ" برای هر کیف پول
   - فیلتر: بر اساس نام کاربر

4. Modal "شارژ کیف پول" (Admin):
   - نمایش نام کاربر
   - نمایش موجودی فعلی
   - فیلد: مبلغ شارژ (الزامی)
   - فیلد: توضیحات (اختیاری)
   - دکمه "شارژ"

5. پیام‌ها:
   - موفقیت: "کیف پول با موفقیت شارژ شد"
   - خطا: "موجودی کافی نیست"
   - هشدار: "آیا از شارژ این کیف پول اطمینان دارید؟"
```

## 4️⃣ ساختار داده (Data Structure)

### چه اطلاعاتی باید ارائه دهید:

```
✅ Entity ها و فیلدهای آن‌ها
✅ روابط بین Entity ها
✅ Enum ها (اگر نیاز است)
✅ Validation Rules
✅ Index ها (برای Performance)
```

### مثال خوب:

```
ساختار داده کیف پول:

1. Entity: Wallet
   - Id: Guid (Primary Key)
   - UserId: Guid (Foreign Key به User)
   - Balance: decimal (موجودی - نمی‌تواند منفی شود)
   - CreatedAt: DateTime
   - UpdatedAt: DateTime?

2. Entity: WalletTransaction
   - Id: int (Primary Key, Auto Increment)
   - WalletId: Guid (Foreign Key به Wallet)
   - TransactionType: enum (Charge, Payment, Refund)
   - Amount: decimal (مبلغ - مثبت برای شارژ، منفی برای پرداخت)
   - Description: string? (توضیحات)
   - RelatedOfferId: int? (اگر تراکنش مربوط به آگهی است)
   - CreatedAt: DateTime
   - CreatedBy: Guid? (Admin که تراکنش را ایجاد کرده)

3. Enum: WalletTransactionType
   - Charge = 1 (شارژ)
   - Payment = 2 (پرداخت)
   - Refund = 3 (بازگشت وجه)

4. Validation:
   - Balance >= 0 (موجودی نمی‌تواند منفی شود)
   - Amount != 0 (مبلغ نمی‌تواند صفر باشد)
   - برای Payment: Amount < 0
   - برای Charge: Amount > 0

5. Index:
   - Wallet.UserId (برای جستجوی سریع کیف پول کاربر)
   - WalletTransaction.WalletId (برای جستجوی تراکنش‌های یک کیف پول)
   - WalletTransaction.CreatedAt (برای مرتب‌سازی)
```

## 5️⃣ امنیت و دسترسی‌ها (Security & Permissions)

### چه اطلاعاتی باید ارائه دهید:

```
✅ چه کسانی می‌توانند چه کاری انجام دهند
✅ Permission های مورد نیاز
✅ Validation های امنیتی
✅ Audit Log (اگر نیاز است)
```

### مثال خوب:

```
امنیت و دسترسی‌های کیف پول:

1. Supplier:
   - می‌تواند موجودی خود را ببیند
   - می‌تواند تاریخچه تراکنش‌های خود را ببیند
   - می‌تواند درخواست شارژ ارسال کند
   - نمی‌تواند موجودی را تغییر دهد
   - نمی‌تواند تراکنش‌های دیگران را ببیند

2. Admin:
   - می‌تواند تمام کیف پول‌ها را ببیند
   - می‌تواند کیف پول را شارژ کند
   - می‌تواند تاریخچه تمام تراکنش‌ها را ببیند
   - نمی‌تواند موجودی را کاهش دهد (فقط شارژ)

3. Permission:
   - Wallet.ViewOwn (مشاهده کیف پول خود)
   - Wallet.ViewAll (مشاهده تمام کیف پول‌ها - Admin)
   - Wallet.Charge (شارژ کیف پول - Admin)

4. Validation:
   - فقط Admin می‌تواند شارژ کند
   - Supplier نمی‌تواند موجودی خود را دستکاری کند
   - مبلغ شارژ باید مثبت باشد
   - موجودی نمی‌تواند منفی شود

5. Audit:
   - تمام تراکنش‌ها باید ثبت شوند
   - Admin که شارژ را انجام داده، باید ثبت شود
   - تاریخ و زمان دقیق تراکنش ثبت شود
```

## 📋 چک‌لیست قبل از ارسال درخواست

قبل از ارسال درخواست، مطمئن شوید که:

- [ ] **هدف و نیاز** به وضوح مشخص شده است
- [ ] **منطق کسب‌وکاری** کامل و بدون ابهام است
- [ ] **جریان‌های کاری** مرحله به مرحله توضیح داده شده‌اند
- [ ] **صفحات و UI** به تفصیل شرح داده شده‌اند
- [ ] **ساختار داده** (Entity ها، فیلدها، روابط) مشخص شده است
- [ ] **محدودیت‌ها و Validation** ها مشخص شده‌اند
- [ ] **دسترسی‌ها و امنیت** مشخص شده‌اند
- [ ] **مثال‌های عملی** (اگر نیاز است) ارائه شده‌اند

## 🎨 مثال کامل یک درخواست خوب

```
===========================================
قابلیت: کیف پول و گردش مالی
===========================================

1. شرح کلی:
هدف: تأمین‌کنندگان بتوانند موجودی کیف پول خود را ببینند و از آن برای پرداخت هزینه آگهی استفاده کنند.

کاربران: Supplier, Admin

ارتباط: با سیستم آگهی‌ها (هزینه انتشار: 10,000 تومان)

2. منطق کسب‌وکاری:
- هر Supplier یک کیف پول با موجودی 0 دارد (خودکار ایجاد می‌شود)
- Admin می‌تواند کیف پول را شارژ کند
- هنگام انتشار آگهی، 10,000 تومان از کیف پول کسر می‌شود
- اگر موجودی کافی نباشد، آگهی منتشر نمی‌شود
- تمام تراکنش‌ها ثبت می‌شوند

3. رابط کاربری:
- صفحه "کیف پول من" برای Supplier:
  * نمایش موجودی (عدد بزرگ)
  * جدول تاریخچه تراکنش‌ها
  * دکمه "درخواست شارژ"
  
- صفحه "مدیریت کیف پول‌ها" برای Admin:
  * لیست کیف پول‌ها
  * دکمه "شارژ" برای هر کیف پول

4. ساختار داده:
- Wallet: Id, UserId, Balance, CreatedAt, UpdatedAt
- WalletTransaction: Id, WalletId, TransactionType, Amount, Description, CreatedAt
- Enum: TransactionType (Charge, Payment, Refund)

5. امنیت:
- Supplier: فقط مشاهده موجودی و تاریخچه خود
- Admin: مشاهده همه + شارژ
- Permission: Wallet.ViewOwn, Wallet.ViewAll, Wallet.Charge
```

## 💡 نکات مهم

### ✅ کارهایی که باید انجام دهید:

1. **جزئیات کامل:** هرچه جزئیات بیشتری ارائه دهید، نتیجه بهتری خواهیم داشت
2. **مثال‌های عملی:** اگر می‌توانید، مثال‌های واقعی از جریان کاری ارائه دهید
3. **تصاویر (اختیاری):** اگر UI خاصی در ذهن دارید، می‌توانید توضیح دهید یا حتی یک Mockup ساده بکشید
4. **اولویت‌بندی:** اگر چند قابلیت دارید، اولویت‌ها را مشخص کنید

### ❌ کارهایی که نباید انجام دهید:

1. **ابهام:** از عبارات مبهم مثل "یک سیستم پرداخت" استفاده نکنید
2. **کمبود جزئیات:** نگویید "یک صفحه برای کیف پول" - بگویید دقیقاً چه المان‌هایی باید داشته باشد
3. **فرض کردن:** فرض نکنید که من می‌دانم چه می‌خواهید - همه چیز را صریح بگویید
